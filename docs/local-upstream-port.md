# Local upstream port — 0.1.6 base and unreleased 0.1.7 extension

## Source and compatibility contract

This local release ports the 0.1.5 ZCode customization onto upstream `b163bbab89741d5dbd412d6421f77a26481cd850` (including the author's chat isolation and exact SCAR-001 exceptions). It is a local integration, not an upstream release or a new publication.

- Preserve upstream per-chat `.scar/sessions/<digest>/` contracts, reports, reviews and gates, host-project bindings across worktrees, shared personal catalog and legacy unsessioned API.
- Keep bounded concurrent fresh-byte snapshots, the Windows/UNC allowance and strict source-hash project exceptions. An exception is explicit, auditable and invalidated by any source change; read `project-exceptions.md` before using it.
- Preserve native ZCode analysis-first mode, trusted owner-bound implementation, one-use PreToolUse transport, documentation-only scope and protected-file baseline, exact-owner archived cancellation, unchanged-failure retry refusal, and optional operator session bridge.
- Native request capabilities live in `request-bindings/`, separate from upstream persistent chat/project records in `bindings/`. `scar_status` and `scar_details` receive a one-use binding too so pooled MCP connections inspect the calling chat's evidence. Analysis/context/catalog remain stateless and issue no capabilities. Evidence inspection does not arm or clear a task.
- Different chats in the same project no longer overwrite each other's contracts/reports/gates. In native ZCode a chat still has only one active owner task; it cannot replace its own unfinished generation implicitly. Codex/Claude use their native declarations and do not activate the ZCode adapter from environment variables.
- An old 0.1.5 root contract is read in place only by its matching trusted owner while that owner has no new scoped contract. Finish or explicitly cancel an active old generation before preparing a new scoped phase. Cancellation retains the old contract and archives its evidence. No installation silently moves, cancels, re-scopes or marks user tasks READY. The changed evidence policy can make old verification STALE; fresh authorized verification is required.
- Compact evidence clips scalar metadata and terminates even when evidence arrays are empty. Counts and exception counts remain available; full evidence is retrieved in bounded pages.

## Shared mandatory project checks — unreleased local 0.1.7

The requested extension uses an explicit `.scar/project-checks.json` file (`schema: 1`, nonempty `checks` array) shared by every chat in the same canonical project. Shared checks are mandatory and additive to per-task checks, including explicitly scoped documentation tasks; they never merge task ownership, reports, reviews or gates. Without the file, existing 0.1.6 behavior remains unchanged. Fourteen filesystem/Workflow regressions pass locally; the initial RED demonstrated seven missing-policy enforcement failures, with additional RED cycles for null/scalar policy and non-string IDs. A real pooled native-hook/MCP regression reproduces missing enforcement against an isolated installed 0.1.6 runtime and passes against rebuilt local bundles, including replay/foreign-owner refusal and independent gates. Final full-suite verification is recorded separately in `verification.md`; source manifests are versioned 0.1.7, without installation or publication.

Preparation and verification validate the policy and reject a conflicting task check with the same ID. Identical definitions execute once. Verification reads the current policy, so an already-prepared task cannot omit newly configured mandatory checks. Source/contract/catalog/policy freshness revokes old evidence when the configuration changes; a task prepared with a policy fails closed if that policy disappears. Analysis creates no policy and executes nothing. This development workspace is explicitly configured with mandatory unit, feature and build checks in its ignored local policy file; existing installed 0.1.6 processes are not upgraded or claimed to enforce that policy. The existing exact exceptions, generated-root exclusions and native trusted bindings remain unchanged.
